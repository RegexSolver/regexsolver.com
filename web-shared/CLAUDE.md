# web-shared — cross-app frontend logic (`@regexsolver/web-shared`)

Tiny raw-TypeScript package consumed by all three frontends (website, console, docs)
as a `file:../web-shared` dependency (npm symlinks it; every consumer uses
`moduleResolution: bundler`, so the `.ts` sources are bundled directly — no build step).

## Modules (exports map in package.json)
- `./consent` — `cookie-consent` cookie (accepted/declined), shared across subdomains
- `./theme` — `theme` cookie (light/dark/system), the cross-subdomain dark-mode choice
- `./analytics` — `initAnalytics(posthog, {token, apiHost, source, debug})`: the canonical
  PostHog config (cookieless `memory` persistence by default, upgraded to `localStorage+cookie`
  when consent is accepted, `cross_subdomain_cookie`) + `applyConsentToAnalytics(consent)`.
  `source` (`"website"`/`"console"`/`"docs"`) is registered as the `app` super property, and
  the hostname-derived `environment` (`dev`/`prod`) as another, so every event carries
  its originating frontend + deployment env for filtering in the shared PostHog project.
  A `local` hostname (localhost / 127.0.0.1 / *.local) skips init entirely — local dev
  never sends events, even with a real token in `.env`
- `./cookie-banner` — `createCookieBanner(cookieDomain)`: framework-free banner behavior
  (`shouldShow`/`decide`), consumed by `./components/CookieBanner`
- `./components/{Logo,CookieBanner,FooterContent}` — the shared React components (see
  "React components" below): the lockup renderer (website + console; the docs use the
  baked-colour `<img>` SVGs because they don't define the identity tokens), the one copy
  of the cookie-banner markup (all three apps; each passes its own `cookieDomain` env +
  privacy anchor), and the footer's inner content (website `Footer.tsx` + docs
  `footer-after` slot; the website passes a `renderLink` that routes internal links
  through next/link, the docs use the plain-anchor default). `FooterContent` owns
  `md:grid-cols-4`, which must equal the number of `FOOTER_COLUMNS` entries
- `./site-links` — `NAV_ITEMS`/`FOOTER_COLUMNS`/`OPERATOR`/`COPYRIGHT` + `resolveSiteLink(link, origins)`
  + `isSiteNavGroup(item)`:
  the header-nav and footer link content shared by the website header/footer and the docs
  (`zudoku.config.tsx` `header.navigation` + `footer-after` slot). Pure data + a resolver —
  each app maps its own env vars to the `origins` (website/docs/console base URLs).
  **Adding or removing a `FOOTER_COLUMNS` entry means updating `md:grid-cols-N` in
  `./components/FooterContent`** (four columns today: FEATURES/HELP/RESOURCES/LEGAL).
  The FEATURES column repeats the header's Features dropdown (the three capability
  pages only — Live demo and Pricing live under RESOURCES), which keeps the section
  pages linked from the docs host too.
- **`NAV_ITEMS` entries are either a `SiteLink` or a `SiteNavGroup`** (`{label, items}`), and a
  group renders as a header dropdown. The docs get that for free: Zudoku's own
  `header.navigation` accepts `{label, items:[{label, to, description}]}` groups. The website
  has no Radix, so `Header.tsx` reproduces the same markup by hand (`NavDropdown`) — the two
  are kept pixel-matched, so a change to one needs the same change to the other. `description`
  is only rendered inside a dropdown; top-level links omit it. Keep descriptions short enough
  to fit two lines in a 186px column: both sides apply `line-clamp-2` and will truncate

## brand/ (assets, not code)
`brand/` is the canonical home of every visual asset, generated by two Python
scripts and copied into each app's `public/` by `scripts/sync-brand.mjs`
(each app's `predev`/`prebuild`) — see `brand/README.md` for the regenerate flow.
- `gen_logo.py` → the lockup/mark SVGs, the favicon rasters, and `src/brand.ts`
- `gen_og.py` → `brand/og/og-{default,docs,console}.png`, the 1200x630 social
  share cards. `sync-brand.mjs` copies each app's variant to its
  `public/og-image.png`, so `og:image` is the constant `/og-image.png`
  everywhere and only the eyebrow + domain line differ per app.
Both scripts need a venv + `brand/martian.ttf` + `brand/jetbrains.ttf`, which are
gitignored build inputs (these are the *rasterizing* inputs for the logo/OG scripts —
unrelated to the webfonts in `fonts/` below); the generated SVG/PNG output is committed.

## fonts/ (assets, not code)

`fonts/` is the canonical, **committed** copy of the three webfonts all three frontends
share — Martian Mono (display), Instrument Sans (body), JetBrains Mono (code). They used
to be fetched from `fonts.googleapis.com` by each app separately; nothing does now, at
build time or at runtime.
- `scripts/fetch-fonts.mjs` regenerates the directory (run by hand, like `gen_logo.py`).
  **All 14 subsets are kept, not just latin** — the landing page's live demo renders
  arbitrary user-supplied regexes, so Cyrillic/Greek/Vietnamese input must still find a
  real face. `unicode-range` means a browser downloads only what a page uses, so the
  212 KB on disk costs nothing at runtime.
- The woff2 filenames carry a **content hash**, which is what lets `rs-website`,
  `rs-console` and `rs-docs.nginx.conf` mark `/fonts/*.woff2` `immutable`.
- `fonts.css` writes `url()`s **root-absolute** (`/fonts/…`): the rules get inlined into
  whichever stylesheet imports them, so a relative path would resolve against the wrong
  base.
- `fonts/preload.ts` (`@regexsolver/web-shared/fonts/preload`) exports `FONT_PRELOAD`, the
  three latin faces worth a `<link rel="preload">`. Generated rather than hand-copied into
  each app's head precisely because the hashed names would rot there silently.

**All three apps import `@regexsolver/web-shared/fonts/fonts.css` through their bundler**,
which inlines the 30 `@font-face` rules into the app's own stylesheet — so `fonts.css` is
never served, and `sync-brand.mjs` copies **only the woff2** into each `public/fonts/`.
The syntax differs because the framework forces it, not the behaviour:
| app | how it imports `fonts.css` |
| --- | --- |
| website (Next) | JS `import "@regexsolver/web-shared/fonts/fonts.css"` in `app/layout.tsx` |
| console (Vite) | CSS `@import "@regexsolver/web-shared/fonts/fonts.css"` atop `src/index.css` |
| docs (Zudoku) | `theme.fonts[*].url` — Zudoku turns it into that same `@import` |

Website and docs additionally preload the three latin faces; the console does not bother.

**Both halves must stay in step**: the CSS is resolved from `node_modules` at build time,
the woff2 it names from `public/` at runtime. Regenerating `fonts/` without re-running
sync-brand leaves the stylesheet pointing at names no longer on disk — `predev`/`prebuild`
run sync-brand so that cannot happen in a normal build.

## scripts/indexnow.mjs (tooling, not code shipped to the apps)

The IndexNow ping, run by the rs-website and rs-docs deploy jobs on **master only**
(`node apps/web-shared/scripts/indexnow.mjs <prod origin>`): it fetches the live
`sitemap.xml` of that origin and submits its URLs so the engines implementing the
protocol (Bing, Yandex, Seznam, Naver — Google does not) recrawl on a push instead of
on their own schedule. It lives here because it is the one thing the website and docs
apps share that isn't bundled; nothing imports it at runtime.
- **The key constant is the single source of truth.** `INDEXNOW_KEY` must equal the name
  and contents of the key file committed in BOTH apps
  (`apps/com.regexsolver/public/7dfa2483f6057cb87aa0cbec916d71cb.txt`,
  `apps/com.regexsolver.docs/public/7dfa2483f6057cb87aa0cbec916d71cb.txt`, each unignored by a `!` line
  in that `public/.gitignore`). Rotating the key = edit the constant, rename both files,
  rewrite their contents.
- **Guards, in order**: the origin must be one of the two prod origins (a dev deploy can
  never submit, even if the workflow condition were wrong); the origin's `<key>.txt` must
  serve exactly the key (turns a half-done rotation into a named failure instead of an
  opaque 403 from the API); the sitemap must be non-empty (an empty one means a non-prod
  build is live on a prod host) and list only URLs under that origin. GETs retry 3x/5s,
  since the ping runs straight after a rolling `docker service update`.
- `--dry-run` prints the payload and submits nothing.

## React components (`src/components/`)
The package ships React components, which required one narrow exception to the
no-runtime-imports rule below. Importing `react` from a symlinked package only works
because every consumer resolves it back to its own copy — each leg is load-bearing:
- **Bundlers**: Next aliases react globally (website); Zudoku's Vite config sets
  `resolve.dedupe: ["react", "react-dom"]` (docs); the console's `vite.config.ts` sets the
  same dedupe (added for this). Without dedupe a second React instance loads and every
  hook crashes.
- **Node + TypeScript resolution**: Zudoku's config loader executes the config graph in
  Node, and tsc/IDEs resolve from the symlinked package's REAL path — both find react via
  the dev-only `react` + `@types/react` in `devDependencies`, installed into
  `apps/web-shared/node_modules` by EVERY app's `predev`/`prebuild`
  (`npm ci --prefix ../web-shared`). CI and Docker get it for free through those scripts.
  Do NOT reach for tsconfig `paths` to map react instead: Turbopack applies the website's
  tsconfig `paths` at RUNTIME (bundling @types/react as react), which is the trap this
  design exists to avoid.
- **Tailwind**: the components' classes live outside every app's own sources. The website
  and console declare `@source "../node_modules/@regexsolver/web-shared/src"` in their
  `index.css` (v4 auto-detection skips node_modules); the docs get it for free because
  Zudoku turns the config's traced dependencies into `@source` entries. Removing a
  component's last usage from an app does NOT remove its CSS there — the whole package is
  scanned.
Components take everything app-specific as props (env-derived values, the privacy anchor,
a `renderLink`), keeping the env-vars-stay-in-the-apps rule intact.

## Hard constraints
- **No runtime imports except `react`** (see above for why react works). A bare
  `import "posthog-js"` still fails Node resolution from the package's real path during
  Zudoku's build-time config load. That's why `initAnalytics` takes the posthog instance
  as a parameter (typed structurally via `AnalyticsClient`). Don't add dependencies here;
  the dev-only `react` + `@types/react` in `devDependencies` are resolution plumbing for
  Node/tsc, not runtime deps — every bundler still uses its app's own React.
- **Env vars stay in the apps.** Each bundler statically inlines its own prefix
  (`NEXT_PUBLIC_*` / `VITE_*` / `ZUDOKU_PUBLIC_*`), so config (token, host, cookie
  domain) is always passed in as arguments from a thin per-app glue module
  (`src/lib/{posthog,theme}.ts` in each app).
- Writes must stay guarded for SSR (`typeof document/window === "undefined"`), since the
  landing (Next) and docs (Zudoku) evaluate these modules during prerendering.
- Changing this package rebuilds all three frontends: it's COPY'd into the three
  Dockerfiles before `npm ci` and listed in all three workflows' path filters.
