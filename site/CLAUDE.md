# com.regexsolver — public landing page, live demo & pricing (Next.js 15 static export)

Marketing site for RegexSolver: home (`/`), `/pricing`, and an interactive `/demo` playground. Built as a fully static export (`output: "export"`) — plain HTML/CSS/JS in `out/`, no server runtime. Not a backend service. The demo's compute call goes to a `/demo` proxy (the `rs-website` demo proxy per root CLAUDE.md), never to `rs-api` (:8888) directly.

## Layout
- `next.config.ts` — `output:"export"`, `trailingSlash`, `images.unoptimized` (no Image server)
- `src/app/{layout,page,demo/page,pricing/page}.tsx` — App Router; each `page.tsx` is a thin wrapper rendering a `views/` component plus its own `metadata` (title/description/canonical/og). `layout.tsx` holds the shared `metadata` (with `metadataBase`, which is what resolves every relative canonical/`og:image` to an absolute URL) and the JSON-LD `Organization`/`WebSite`/`SoftwareApplication` graph
- `src/app/{sitemap,robots}.ts` — generated `sitemap.xml` + `robots.txt` (`force-static`, so they are emitted into `out/`)
- `src/views/{LandingPage,LiveDemo,Pricing,NotFound}.tsx` — actual page UI (all `"use client"`). `LandingPage` is deliberately short on prose. The hero carries the product, in three bands: headline with the sentence under it on top; then, side by side, a grouped legend of eleven operations under the API's tag groups (analyze / compute / generate), and `components/HeroFigure.tsx` — FIG. 1, one drawing per operation family (Venn diagram for set operations, dot field for cardinality, character cells for length, string tiles for generation, joined blocks for concatenation, repeated blocks for repeat; the overlap ink always marks the result), plus the same call as an SDK snippet in the shared `CustomCodeTabs` (its `flush` prop drops the outer border for embedding) from `generateShortSnippet` with its variables renamed to a/b, and the typed-out result; the legend is its control, state lives in `LandingPage`; then two `ActionLink` cards side by side. Everything below adds only what the hero cannot: the install-and-chaining snippet (`generateLandingSnippet`) in `CustomCodeTabs`, a five-row how-it-works list, links to the three feature pages with their descriptions, FAQ. Editable `SectionExampleCard`s live on the section pages only; the hero's two action cards are the page's only CTA. The operations table lives on the section pages only. Keep new copy to one line per block; the examples carry the explanation. The figure takes its examples from `lib/sections.tsx` via `findExample`. `NotFound` renders via `app/not-found.tsx` into the export's `404.html`, which rs-website serves (with a real 404) for every dead URL — full chrome + links, no canonical/sitemap/breadcrumb entry. The export also writes it as `404/index.html` and `_not-found/index.html`; rs-website answers those three paths (and `/404`, `/_not-found`) with a 404 too, so the not-found page never exists as a 200 URL of its own, and it 301s every `index.html` form onto the directory URL. Both `robots` and `alternates.canonical` are explicitly `null` there, and both have to be: Next adds its own `<meta name="robots" content="noindex">` to a not-found route, so omitting the keys inherits the layout's `index, follow` and `canonical: "/"` alongside it — a 404 that both contradicts its own noindex and claims to be the homepage. `undefined` does not clear them; only `null` does
- `src/lib/faqs.tsx` — the landing FAQ, one source for the visible accordion (`LandingPage`) and the `FAQPage` JSON-LD (`app/page.tsx`): paragraphs carry plain `text` for the structured data plus an optional `node` when the rendered form needs markup; keep the two saying the same thing
- `src/views/SectionPage.tsx` — one component rendering ALL THREE product section pages (`/regex-analysis/`, `/pattern-manipulation/`, `/strings-generation/`) from a `Section` object; there is no per-page layout code
- `src/lib/sections.tsx` — the three `Section` definitions (title/description/heading, 1-2 sentence intro, worked examples, op rows, optional parameter rows, `furtherReading` topic links that together cover every row; the hero's Documentation card always goes to `/quickstart`). Adding or editing a feature page means editing this file, not `SectionPage.tsx`. **Every example result must be vetted** — taken from the docs examples or provable by hand (16^5, set identities); the file's header comment says so. The landing page's live cards are these same examples, picked by `demoOp` (`LandingPage.tsx`), so a change here shows up on `/` too. An example with `demoOp` renders as a live card (`components/SectionExampleCard.tsx`): editable patterns (plus limit/offset for `strings`, min/max for `repeat`), a COMPUTE button POSTing to the same `/demo` proxy as LiveDemo, and an OPEN IN LIVE DEMO deep link carrying the current inputs (`/demo?op=…&a=…&b=…`, the URL shape LiveDemo parses); the vetted precomputed result is the initial, prerendered state. Leave `demoOp` off when the demo cannot reproduce the call (e.g. generation's length-window options) — the card then renders read-only. The page's code block is `generateSectionSnippet(slug, lang)` in `generateCode.ts` — one hand-authored multi-operation overview per section, same result-vetting rule
- `src/lib/operations.tsx` — `ANALYZE_ROWS`/`COMPUTE_ROWS`/`GENERATE_ROWS` + `OpTableRows`, the operation-table data shared by the landing page (all groups in one table) and the section pages (one group each), so the two cannot drift. Each row's `doc` is a docs-site path + heading anchor, rendered as a link on the operation name; renaming a docs heading breaks it
- `src/components/JsonLd.tsx` — server component wrapping a `<script type="application/ld+json">`, so structured data stays out of the client bundle
- `src/lib/generateCode.ts` — builds Java/JS/Python SDK snippets from an `{operationId}` + payload; exports `generateShortSnippet`/`generateFullSnippet` (LiveDemo uses full) plus two hand-authored overviews: `generateSectionSnippet(slug, lang)` (section pages) and `generateLandingSnippet(lang)` (the landing page's one code block: client setup and a result chained into the next call, results as comments, same vetting rule)
- `src/components/{Header,Footer,CodeBlock,CustomCodeTabs}.tsx` — shared chrome + Prism code rendering. Every `CustomCodeTabs` shares one selected language (`src/lib/codeLanguage.ts`, a `useSyncExternalStore` store persisted to `localStorage["code-language"]`): picking a language switches all blocks on the page and the next page opens on it. It matches tabs on their Prism `language`, not `value` (LiveDemo's values differ from the other pages'), and prerenders the first tab, so the stored choice appears after hydration `Footer` is a thin shell around web-shared's `FooterContent` (it owns the `<footer>` wrapper and passes a `renderLink` that routes internal links through next/link); `CookieBanner.tsx` and `Logo.tsx` are thin wrappers/re-exports of the web-shared components (see its CLAUDE.md)
- `src/components/DotGraph.tsx` — renders Graphviz DOT source as inline SVG for the demo's `dot` op, via a lazily-imported `@viz-js/viz` (Graphviz compiled to WASM, ~1.2 MB, embedded in the JS so there's no separate `.wasm` fetch). Graphviz's literal `black` strokes/fills are remapped to `currentColor` in CSS so the diagram follows the theme
- `src/components/ActionLink.tsx` — the site's one call-to-action style: an index row (optional `01`/`02` number, label, mono-caps note, arrow that slides on hover; ↗ when the target leaves the site, → otherwise; `primary` sets the label in set-a). Used by the landing hero and CTA, the section-page hero, the pricing card and the 404 page. `ui/Button` is no longer used for calls to action — reach for `ActionLink`
- `src/components/ui/{Link,Button,ThemeContext}.tsx` — primitives
- `src/index.css` — Tailwind v4 `@import "tailwindcss"` + `@custom-variant dark` + `:root`/`.dark` CSS-var blocks + `@theme` design tokens. `--popover` is the one token whose dark value is not a pure recompute: it mirrors the docs theme (`zudoku.config.tsx theme.dark.popover`), which lifts 4% off the page in dark mode only, so the header dropdown's surface matches on both sites
- `.env.local` — `NEXT_PUBLIC_DEMO_BACKEND_URL` (`http://127.0.0.1:8080`), `NEXT_PUBLIC_CONSOLE_URL` (`http://127.0.0.1:5173`), `NEXT_PUBLIC_DOCS_URL` (docs-site host), `NEXT_PUBLIC_SITE_URL` (`http://localhost:3000` — anything but the prod origin builds with noindex, see `seo.ts`), `NEXT_PUBLIC_POSTHOG_{PROJECT_TOKEN,HOST}` (analytics), `NEXT_PUBLIC_COOKIE_DOMAIN` (consent-cookie parent domain, unset on localhost)
- `src/lib/posthog.ts` + `instrumentation-client.ts` + `src/components/CookieBanner.tsx` — PostHog analytics + consent, all logic from `@regexsolver/web-shared` (`apps/web-shared`, raw-TS `file:` dep — see its CLAUDE.md): cookieless `memory` persistence by default, upgraded to `localStorage+cookie` when the `cookie-consent` cookie (shared across subdomains via `NEXT_PUBLIC_COOKIE_DOMAIN`) is `accepted`; the console + docs apps use the same package, and prod points `NEXT_PUBLIC_POSTHOG_HOST` at the same-origin `/ingest` proxy in rs-website. Requires `transpilePackages` in `next.config.ts`. `src/lib/posthog.ts` runs `initAnalytics(...)` and exports the `posthog` instance + an `analyticsEnabled` flag (false when `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN` is unset or on a local hostname — local dev never inits PostHog); `instrumentation-client.ts` is just a side-effect import of it so PostHog is ready at the Next entry point. Views (`LandingPage`/`Pricing`/`LiveDemo`) import from `../lib/posthog` and guard every custom `posthog.capture(...)` (funnel/demo events like `get_started_clicked`, `demo_operation_run`) on `analyticsEnabled`
- `src/lib/docs.ts` — `docs(path)` helper: prefixes docs-site links with `NEXT_PUBLIC_DOCS_URL` (baked at build time per env)
- `src/lib/seo.ts` — `SITE_URL` (the prod origin, also on the dev deploy: canonicals always point at prod) + `IS_PROD_SITE` (the indexing switch, mirroring the docs site: only the build whose `NEXT_PUBLIC_SITE_URL` is the prod origin gets indexable pages, a populated sitemap and a robots.txt sitemap line — dev and local build with `noindex, nofollow`, so the cross-host canonical is a belt-and-braces second signal, not the only one) + `OG_IMAGE`, the 1200x630 share card. Imported by `app/layout.tsx`, both page `metadata` exports, `app/sitemap.ts` and `app/robots.ts` — the single place the origin is written. Also `breadcrumb(trail)`, which builds the `BreadcrumbList` JSON-LD behind the `regexsolver.com › …` trail in a Google result
- `public/7dfa2483f6057cb87aa0cbec916d71cb.txt` — the **IndexNow** key file, served at `https://regexsolver.com/7dfa2483f6057cb87aa0cbec916d71cb.txt` (`public/.gitignore` ignores `*`, so it carries its own `!` line). The key itself lives once, in `apps/web-shared/scripts/indexnow.mjs`; the rs-website workflow runs that script against the prod origin after every **prod** deploy, which reads the live `sitemap.xml` and submits its URLs to the engines that implement the protocol (Bing, Yandex, Seznam, Naver — not Google). Rotating the key means editing the constant AND renaming this file and the docs app's copy. The dev image serves the same key file, harmlessly: the script refuses any origin that isn't prod, so dev URLs are never submitted

## How it works
- Everything is pre-rendered at build. The only runtime data flow is `LiveDemo`: pick an op (the `OPS` table sets `args` count + an optional `extra: "repeat"`/`"strings"` flag that reveals min/max or limit/offset params), client-validates patterns with `new RegExp()`, then `POST ${NEXT_PUBLIC_DEMO_BACKEND_URL}/demo` with the form-state JSON (`{operation, regex1, regex2?, min?, max?, limit?, offset?}`, i.e. `currentParams`). Response is read as `{data, error}`; on success `data` (`{type, value}`) renders via `CodeBlock`. A `lastParams` guard suppresses duplicate submits.
- SDK code samples are generated entirely client-side by `generateCode.ts` from a separate `examplePayload` (`{term|terms, min/max, limit/offset}`) — no network call. This payload shape differs from the one POSTed to `/demo`.
- Dark mode: `ThemeContext` toggles the `.dark` class on `<html>`, persisted to `localStorage["theme"]` — and cross-subdomain via the `theme` cookie (`src/lib/theme.ts`, a thin glue over `@regexsolver/web-shared/theme` binding `NEXT_PUBLIC_COOKIE_DOMAIN`): on load the cookie wins over localStorage (`system` resolves via `prefers-color-scheme`); explicit `setTheme` calls write it back so the choice follows the user to the console + docs. `Header` injects global Prism token CSS vars via inline `<style>`; the `fade-in` keyframes + `.animate-fade-in` live in `index.css`.

## Conventions
- Keep `app/**/page.tsx` thin; put UI/logic in `views/` + `components/`. Stateful components need `"use client"`.
- Navigate with the local `<Link to=...>` (`components/ui/Link`) rather than importing `next/link` directly — it wraps `next/link` for internal links but auto-splits external (`to` starts with `http`/`//` → plain `<a target=_blank rel=noopener>`) and exposes `to` instead of `href`.
- Browser config via `NEXT_PUBLIC_*` env vars only.
- **URLs in metadata carry the trailing slash** (`/demo/`, not `/demo`) because `next.config.ts` sets `trailingSlash: true`. A canonical or `<loc>` without it points at a redirect. New page = add its `metadata` (with `alternates.canonical`), a `<JsonLd data={breadcrumb(...)}/>`, a row in `src/app/sitemap.ts`, and an entry in `TRAILING_SLASH_PATHS` in `crates/rs-website/src/main.rs` (which 301s the extensionless form to the canonical one — an export can't emit redirects, so the server does it); the `openGraph` block comes from the `og(...)` helper in `src/lib/seo.ts` — Next does NOT deep-merge `openGraph`, so a hand-written object silently drops `og:site_name`/`og:locale`/`og:type` on that page — and the share image from its `OG_IMAGE`, never a hand-written path. Metadata titles aim for 50-60 chars including the ` | RegexSolver` template (pages keep a short `title` for the breadcrumb and use a longer `metaTitle` for `metadata`/og/twitter; sections carry it as `Section.metaTitle`).
- **The three section pages exist to be indexable, so keep them substantive.** They were added because the site had only three pages on the main host, which is too small a pool for Google to build a sitelink block from, and they reuse the slugs the site served before those pages 404'd so old inbound links land on content again. A stub page is worse than no page here: it is thin content on the host you want ranking. Every capability named in `sections.tsx` is one `shared/openapi.yaml` or the docs actually document.
- `src/index.css` declares `@source "../node_modules/@regexsolver/web-shared/src"` — web-shared's component classes live outside this app's sources and Tailwind v4 auto-detection skips node_modules; drop the directive and the footer/banner silently lose their styling.
- **Never add react/react-dom to tsconfig `paths`**: Turbopack applies them at RUNTIME, so a types-oriented mapping (react → @types/react) breaks the build. web-shared's react types resolve through its own dev-only node_modules (installed by `predev`/`prebuild`), which is why no mapping is needed. `npm run typecheck` = `tsc --noEmit`.
- Style with Tailwind v4 token utilities (`bg-background`, `text-foreground`, `border-border`, `bg-primary`, `bg-muted`, `bg-card`) from `index.css @theme`, plus the `dark:` variant — never raw colors.

## Gotchas
- Static export: no SSR/ISR/route-handlers/middleware/`next/image` optimization. Dynamic behavior must be client-side fetch (as `LiveDemo` does).
- **Fonts are self-hosted, not fetched from Google.** `app/layout.tsx` does `import "@regexsolver/web-shared/fonts/fonts.css"` — Turbopack inlines those 30 `@font-face` rules into the app's CSS chunk and leaves their root-absolute `/fonts/*.woff2` URLs alone, which is where the `prebuild` sync-brand step puts the files (`public/fonts/`, see web-shared's CLAUDE.md). The old Google `<link>` tags and their two `preconnect`s are gone. Note the shape of the fix that came before: an *external* `@import url(...)` in `index.css` is silently dropped by Next/Turbopack and once rendered the whole site in fallback fonts — a bare package specifier is a different mechanism and does get bundled. The three latin faces are preloaded through `ReactDOM.preload` rather than a `<link>` in the JSX, because React 19 hoists preload links into `<head>` itself and a literal element gets emitted twice; the hrefs come from the generated `FONT_PRELOAD` since the filenames carry a content hash.
- `/demo` target comes from `NEXT_PUBLIC_DEMO_BACKEND_URL` (the demo proxy), NOT `rs-api` directly. If unset it falls back to `""` → relative `/demo`.
- Docs-site pages (`/quickstart`, `/privacy`, `/terms`, `/plans-pricing`) have no route in this app — they live on the docs site, so links use `docs("/quickstart")` (`src/lib/docs.ts`), which prefixes `NEXT_PUBLIC_DOCS_URL`. When that var is unset they fall back to relative paths (404 in isolated local dev). `/privacy` and `/terms` are still indexed on this host from the pre-rewrite site, so `crates/rs-website` 301s those two paths to the docs site; a page added here under either slug would be shadowed by that redirect.
- `Header` has a **Features dropdown** (the old "Product" dropdown was removed when `/regex-analysis`, `/pattern-manipulation` and `/strings-generation` 404'd; those pages exist again). Nav (Features ▾ · Live Demo · Docs · Pricing · Open Source ↗) and footer columns render from `@regexsolver/web-shared/site-links`, shared with the docs header/footer (`zudoku.config.tsx`) — edit link content there, not here. From `lg` the nav is absolutely centred in the bar to pixel-match the docs.
- The dropdown is the local `NavDropdown` in `Header.tsx`, hand-written to match what Zudoku renders on the docs for the same `SiteNavGroup` (Radix NavigationMenu). Parity is MEASURED off the docs' rendered panel, not read from its source — Zudoku's theme derives values that differ from its class names (`rounded-md` → 2px, items → 0px, label→description spacing 10px via `gap-1` + `mt-1.5`), which is why the markup carries `rounded-[2px]`, no item rounding, and `mt-2.5`. The details that carry positioning and will break it if changed in isolation: the panel is anchored to the `<nav>` (not the trigger) because Zudoku centres its viewport under the whole nav; the nav AND the dropdown wrapper are `h-9` — the wrapper must fill the nav's height so its hover area touches the panel, otherwise there is a dead strip between trigger and panel where `mouseleave` closes the menu mid-travel; and the panel is `p-2 pr-2.5` around a `w-100` list, matching Zudoku's 418px viewport. Click is open-only, not a toggle: hover has already opened the panel, so a toggle turns the first click into close-and-strand. Closing is leave, Escape, or outside click.
- `Button` with `asChild` clones its single child and merges the button classes into it (a minimal Slot; no Radix dep here) — `asChild` around a `Link` yields one styled `<a>`, so the whole padded surface is clickable. It used to wrap the child in a `<span>`, which left the padding dead to clicks.
- `ThemeProvider` initializes to `light` and only reads `localStorage`/`prefers-color-scheme` in a post-mount effect. A pre-hydration inline `<script>` in `layout.tsx` applies `.dark` before first paint (no white flash for dark-mode visitors), mirroring the provider's resolution order (cookie → localStorage → OS); keep the two in sync. `layout` sets `suppressHydrationWarning` on `<html>` to absorb the class mismatch.
- Pricing Free-plan limits are hardcoded strings in `Pricing.tsx` (`freePlanLimits`) and can drift from real backend quotas.
- `CodeBlock` only imports java/python/javascript Prism langs (and maps `"js"`→`javascript`); `generateCode.ts`'s switch handles more `operationId`s (`empty`,`total`,`pattern`,`empty_string`) than the demo `OPS` list exposes, and `LiveDemo` calls `CodeBlock` with `regex`/`typescript` languages that aren't loaded (so those go unhighlighted).
